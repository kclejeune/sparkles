> Phase 2 adds administration, bounded RDF streams, RDF/JS Source/Store adapters,

This spec's sources are the Sparkles code, the Python bindings of
[P01](P01-python-bindings.md), the Rust client of [P02](P02-rust-client.md), the OpenAPI
description of [X03](X03-openapi-and-completions.md), the napi-rs documentation, the
RDF/JS data model, dataset, stream and query specifications with the `@rdfjs/types`
package, the public documentation of N3.js, rdf-ext and Comunica, the documentation and
published type declarations of Oxigraph's JavaScript package (MIT OR Apache-2.0), the
documentation of Bun and Deno on Node-API, the Node.js release schedule, and the
documentation of openapi-typescript. §17 lists them.

The bindings depend on these parts of Sparkles:

* the embedded API in `crates/sparkles/src/dataset.rs` (`Dataset`, `Transaction`,
  `QuadIter`) and the additive APIs that P01 added for Python, such as
  `Transaction::insert_linked`, `query_with` and `update_with`;
* `sparkles::sparql::{query, QueryOptions, QueryResult}`, `sparkles::sparql::update`
  and `update_in`;
* `sparkles::io`, `sparkles::codec` and `sparkles::jena_formats` for loads and dumps;
* `sparkles::commit` for receipts, `sparkles::history` for past states, and
  `sparkles::stored` for stored queries;
* the public entry points of `sparkles-reasoner`, `sparkles-shacl` and `sparkles-shex`.

The remote client depends only on the HTTP API and its OpenAPI description.

## 1. Summary, goals, non-goals

JavaScript is the language of most web back ends, of serverless functions, of Electron
applications and of a large part of the RDF tooling, such as N3.js, rdf-ext, Comunica,
clownface and the SHACL engines written for RDF/JS. A JavaScript program that wants
Sparkles today must run `sparkles serve` and speak HTTP to it, and it has no typed client
for that either. The UI has a typed client in `ui/src/lib/api.ts`, but that file is part
of the UI and is not published.

This spec adds two npm packages. The engine package embeds Sparkles in a Node.js process
through a native addon built with napi-rs from a new crate, `crates/sparkles-node`. It
opens persistent or in-memory datasets, runs SPARQL queries and updates, loads and dumps
RDF through streams, and runs transactions, all off the JavaScript thread. Its terms are
RDF/JS terms. The client package is a small TypeScript library for a remote Sparkles
server, with types generated from the OpenAPI description. It runs in Node.js, Bun,
Deno, browsers and edge runtimes, because it needs only `fetch` and Web Streams.

**Goals**

* **One process, no server.** The engine package links the engine. A Node.js program
  needs neither a running server nor HTTP.
* **The event loop never waits for the engine.** Every call that can take longer than a
  few microseconds returns a promise and runs on a thread the binding owns. The
  JavaScript thread only converts arguments and builds result objects, and it builds
  them in batches.
* **Results stream with backpressure.** Queries return async iterables. The binding
  decodes the next batch of rows only when the consumer asks for it, and loads and dumps
  move through Node.js and Web streams in bounded chunks.
* **RDF/JS everywhere.** Terms, quads, the data factory and the result bindings follow the
  RDF/JS specifications and their `@rdfjs/types` typings, including RDF 1.2 directional
  literals and triple terms. Terms from N3.js, rdf-ext or any other RDF/JS factory are
  accepted as they are.
* **A familiar shape.** Names follow the Python package where the concept is the same,
  and the RDF/JS names where the specifications have one, such as `match`, `size` and
  `queryBindings`. Code written for Oxigraph's JavaScript package moves over with small
  changes.
* **Typed.** Both packages ship TypeScript declarations. The native layer's declarations
  are generated by napi-rs, and a test checks the published packages' types.
* **Prebuilt binaries.** `npm install` downloads one prebuilt addon for the platform and
  needs no Rust toolchain. Building from source remains possible.
* **The same code locally and remotely.** The engine's `Dataset` and the client's
  `RemoteDataset` implement one TypeScript interface for queries and updates, and both
  throw the same error classes. Code written against the interface runs on either.

**Non-goals**

* **The HTTP server from JavaScript.** `sparkles serve` stays a separate binary. A
  JavaScript program that wants an HTTP endpoint over an embedded dataset writes its own
  route, and §5.5 makes that cheap with results serialized on the engine's threads.
* **A browser build of the engine in Phases 1 and 2.** §12 describes what one would take.
  Browsers use the client package against a server.
* **A synchronous API.** No method blocks the event loop on the engine. RDF/JS's
  synchronous `DatasetCore` is not implemented by `Dataset`, for the reasons of §14.
  Open question 3 considers a read-only variant.
* **Windows in Phase 1.** Phase 1 builds and tests on Linux and macOS, as P01's first
  phase did. Windows joins in Phase 2, where the Python wheels already show the engine
  builds there.
* **Publishing in Phase 1.** Phase 1 builds packages locally and in CI. The publish job
  exists and is gated, as the Python release workflow is.

## 2. Packages and layout

### 2.1 Names

| Package | Contents | Runtime |
|---|---|---|
| `@sparkles-rdf/engine` | The embedded engine. A TypeScript layer over the native addon. | Node.js, and Bun and Deno through Node-API |
| `@sparkles-rdf/engine-<platform>` | One prebuilt addon each, such as `@sparkles-rdf/engine-linux-x64-gnu`. | The platform it names |
| `@sparkles-rdf/client` | The client for a remote server. Pure TypeScript with generated API types. | Any runtime with `fetch` and Web Streams |
| `@sparkles-rdf/common` | The term classes and data factory, the error classes, the receipt types and the shared `SparqlDataset` interface. Pure TypeScript. | Any |

The scope matches the Python distribution name, `sparkles-rdf`, because a short name
like `sparkles` is likely taken on npm. Open question 1 covers the name.

The common package exists so that the engine and the client share their term classes,
error classes and interfaces. Without it, `err instanceof SparqlSyntaxError` would be
false for an error from the other package, and code written for one could not take the
other. The common package has no runtime dependencies. It depends on `@rdfjs/types` for
type declarations only.

### 2.2 Layout

```
crates/sparkles-node/      the cdylib crate, its own cargo workspace and Cargo.lock
  Cargo.toml
  build.rs                 napi-build's link setup
  src/                     the native module
js/
  pnpm-workspace.yaml      the workspace of the three TypeScript packages
  common/                  @sparkles-rdf/common
  engine/                  @sparkles-rdf/engine: TypeScript layer, generated loader and
    npm/                   binding declarations, one directory per platform package,
    test/                  and the tests
  client/                  @sparkles-rdf/client, with src/openapi.d.ts generated
```

The crate is kept out of the root workspace and has its own `Cargo.lock`, for the
reasons of [P01 §2.2](P01-python-bindings.md#22-keeping-the-crate-out-of-the-default-workspace).
A Node-API addon leaves the Node-API symbols undefined for the host to provide, so its
test targets do not link on macOS without extra flags, and `cargo test --workspace` would
compile napi-rs for every developer. A `node:lock` task refreshes the lock from the root
lock, as `py:lock` does.

The napi-rs CLI builds the crate with `--manifest-path ../../crates/sparkles-node/Cargo.toml`
from `js/engine` and writes the addon, the loader and the binding declarations there. The
UI keeps its own pnpm project in `ui/`. It can depend on the client through a `link:`
dependency when it adopts it (open question 6).

### 2.3 Versions

The three packages and the platform packages are versioned in lockstep with the
Sparkles workspace version, as the Python package is. A release tag `js-v<version>`
publishes all of them. The engine package pins its platform packages and the common
package to the same exact version.

The client works with servers of the same and older versions. It reads the server's
version from `GET /$/server` and, for an operation the server lacks, throws
`UnsupportedError` with the server's 404 rather than a generic HTTP error. The client's
`openapi.d.ts` records the OpenAPI document it was generated from.

### 2.4 Module format and runtimes

The packages are ES modules only. Node.js 22.12 and later can `require` an ES module, so
CommonJS callers still load them. The `engines` field is `node >=22.12`.

Phase 1 supports and tests Node.js 22, 24 and 26. Node.js 22 is in maintenance until
April 2027, Node.js 24 is in long-term support until April 2028, and Node.js 26 enters
long-term support at the end of October 2026. The addon targets Node-API version 9, which
all three provide, and the napi-rs crate's `napi9` feature enforces that floor at
compile time.

Bun loads Node-API addons, and its documentation says most work without changes. napi-rs
lists Bun as best-effort support. Deno loads Node-API addons from npm packages when the
project has a `node_modules` directory and the program runs with `--allow-ffi`. napi-rs
does not test Deno. Both runtimes are therefore Phase 2 targets with their own CI jobs,
and the package documents only what those jobs pass.

### 2.5 Cargo features and the allocator

The crate has the features of the Python crate, with the same defaults: `reasoning`,
`shacl`, `shex`, `text` and `geo`, with zstd and brotli always on. A method whose feature
is missing throws `UnsupportedError` that names the feature, and `FEATURES` lists the
build's features.

The addon uses the system allocator, as the Python extension does. Rust's global
allocator in a `cdylib` covers only the addon's own allocations, so mimalloc would not
change how Node.js allocates. It could still pay off on musl, whose allocator is slow
under threads. Open question 4 decides it after the Phase 1 benchmark.

## 3. The engine API

The TypeScript declarations in `js/engine/src/index.ts` are the reference. The examples
use top-level `await`. Times are in milliseconds, as is usual in JavaScript.

### 3.1 Datasets

```ts
import { Dataset, factory } from '@sparkles-rdf/engine';   // re-exports the common package

const mem = Dataset.memory();                         // synchronous, nothing to wait for
const ds = await Dataset.open('mydb', {               // creates the directory if missing
  unionDefaultGraph: false,
  readOnly: false,
});
ds.path;                                              // null for an in-memory dataset
await ds.close();
await using db = await Dataset.open('other');         // closes at the end of the scope
```

`Dataset.open` is asynchronous because opening replays the write-ahead log and may build
an index. A database directory stays locked while it is open, and a second process gets
`DatasetLockedError`.

Inside one process, the addon keeps a registry of open stores by canonical path. A
second `Dataset.open` of the same directory, from the main thread or from a
`worker_threads` worker, returns a new handle on the same store instead of failing on
the lock. Node.js loads one copy of an addon per process and runs it in every worker, so
the registry lets several workers share one engine and its caches. The options must
match the first open, or `open` throws `InvalidInputError`. The directory is released
when the last handle closes.

`close()` waits for the queries and transactions of the handle to end, then releases it.
The handle also implements `Symbol.asyncDispose`, so `await using` closes it. A handle
that is garbage-collected without `close()` is released by its finalizer, but the time of
that is up to the garbage collector, so code should close datasets it opens.

### 3.2 SPARQL queries

```ts
const result = await ds.select(`
  PREFIX foaf: <http://xmlns.com/foaf/0.1/>
  SELECT ?person ?name WHERE { ?person foaf:name ?name } ORDER BY ?name`);
result.variables;                         // [Variable('person'), Variable('name')]
result.size;                              // the number of rows, known once it resolves
for await (const row of result) {
  row.get('name');                        // a Literal, or undefined when unbound
  row.get(factory.variable('person'));    // RDF/JS Bindings take a Variable too
  row.toObject();                         // { person: NamedNode, name: Literal }
}
const rows = await (await ds.select(q)).toArray();

await ds.ask('ASK { ?s ?p ?o }');          // boolean
for await (const quad of await ds.construct(q)) { /* RDF/JS Quad */ }
const any = await ds.query(q);            // a union discriminated by `type`
```

`query` resolves to a `BindingsResult` (`type: 'bindings'`), a `BooleanResult`
(`type: 'boolean'`) or a `QuadsResult` (`type: 'quads'`). `select`, `ask` and
`construct` check the query form and throw `InvalidInputError` for another form, which
gives TypeScript the narrower type.

The promise resolves once the query has run. The engine evaluates a query into a table of
ids before it returns anything, so syntax errors, timeouts and budget errors surface as a
rejected promise and never in the middle of an iteration. That also makes `size` known
before the first row is read. Iteration then turns ids into terms in batches (§6.2).

Each row is a `Bindings` object of the RDF/JS query specification. It has `type`,
`size`, `get`, `has`, `keys`, `values`, `forEach`, `equals`, `filter`, `map`, `merge`
and iteration over `[Variable, Term]` pairs. `get` also accepts a plain variable name.
`toObject()` returns a plain object of the bound variables, which is the form most
application code wants.

A `QuadsResult` yields RDF/JS quads. CONSTRUCT templates with `GRAPH` blocks yield quads
in named graphs, and DESCRIBE follows the dataset's setting or the `describe` option.

The options of every query method are these.

| Option | Meaning |
|---|---|
| `baseIri`, `prefixes` | The base IRI and prefixes for the query text. |
| `bindings` | Pre-bound variables, as `{ name: Term }` or a `Bindings`. It sets `QueryOptions::initial_bindings`. |
| `defaultGraph`, `namedGraphs` | The query's dataset, like the protocol's `default-graph-uri` and `named-graph-uri`. |
| `includeInferred` | Merges the reasoner's graph into the default graph. |
| `at` | A past state, as a commit number, a `Date`, or a string like `snapshot:name` (§3.8). |
| `timeout` | A time limit in milliseconds. |
| `signal` | An `AbortSignal` that cancels the query (§5.3). |
| `maxRows`, `maxMemoryBytes`, `maxRowsProduced` | The budgets of `QueryOptions`. |
| `describe` | A DESCRIBE mode, or an object of DESCRIBE options. |
| `factory` | An RDF/JS data factory for the result terms (§6.3). |
| `batchSize` | Rows per batch decoded off the JavaScript thread (§6.2). |

### 3.3 Updates and receipts

```ts
const r = await ds.update('INSERT DATA { <urn:a> <urn:p> 1 }', { message: 'seed' });
r.inserted; r.deleted;                     // counts of quads
r.receipt.committed;                       // false when nothing changed
r.receipt.commit.seq;                      // the commit's sequence number
```

Updates, loads, `addAll` and transactions return a `CommitReceipt`. Its shape is the JSON of `sparkles::commit::Receipt`
that the server returns, with `datasetId`, `committed`, `commit` (sequence number, kind,
counts, time, message and change digest) and `validation` when a write guard ran. The
common package defines the type once, so a receipt from the engine and one from the
client are the same type.

Update options are `baseIri`, `prefixes`, `timeout`, `signal`, `message`, `ifHead` and
`noWait`. `ifHead` is a commit number that must still be the head, which is the engine's
write precondition. `noWait` makes a write fail with `ConflictError` instead of waiting
when another write holds the writer.

### 3.4 Quads

```ts
await ds.add(quad);                        // true when it was new, one commit
await ds.delete(quad);
const { inserted, receipt } = await ds.addAll(quadsOrAsyncIterable);   // one commit
await ds.has(quad);
await ds.count();                          // the number of quads
for await (const q of ds.match(alice, null, null, null)) { … }
await ds.match(alice).toArray();
await ds.graphs();                         // named graph names
await ds.clearGraph(graph);
```

`match` follows RDF/JS: `null` or `undefined` matches anything, and a `graph` of `null`
matches every graph while `factory.defaultGraph()` matches only the default graph. The
result is an async iterable read from one snapshot in batches of index keys, through
`Dataset::quads`. It also has `toArray()`, and `toStream()` returns an RDF/JS `Stream`
for code that wants events (§9.1).

`addAll` accepts an array, an iterable or an async iterable of quads and writes them in
one commit. Triples, which RDF/JS represents as quads in the default graph, go to the
default graph.

Blank nodes follow the Rust API and the Python package. A blank node read from the
dataset has a label like `b1f` that names the stored node in later patterns, bindings and
writes. Any other label names a new node in each write, and the same label within one
`addAll` or transaction names one node.

### 3.5 Transactions

```ts
const { value, receipt } = await ds.transaction(async (tx) => {
  await tx.add(quad);
  await tx.delete(other);
  for await (const q of tx.match(alice)) { … }      // sees the transaction's changes
  await tx.update('DELETE WHERE { ?s <urn:old> ?o }');
  const n = await tx.select('SELECT (COUNT(*) AS ?n) WHERE { ?s ?p ?o }');
  return n;
}, { signal, timeout: 30_000, message: 'nightly import' });
```

The callback runs while the transaction holds the dataset's single writer. It commits
when the callback's promise resolves and rolls back when it rejects. The transaction's
methods see its own uncommitted changes. Queries on the dataset during the transaction
read the last commit. After the callback settles, every method of `tx` rejects with
`InvalidInputError`, which catches a `tx` that escapes its callback.

`transaction` resolves to `{ value, receipt }`. Code that does not need the receipt
destructures `value`.

Explicit transactions exist for code that cannot use a callback:

```ts
await using tx = await ds.beginTransaction();       // rolls back at scope end unless committed
await tx.add(quad);
const receipt = await tx.commit();
```

§5.4 explains how a transaction maps onto the engine's single writer without blocking a
thread, and how the binding stops a callback from deadlocking on its own transaction.

### 3.6 Loading and dumping

```ts
await ds.load({ path: 'data.ttl.gz' });                       // format and codec from the name
await ds.load(text, { format: 'turtle', toGraph: g });
await ds.load(fs.createReadStream('data.nq.zst'), { format: 'nq' });   // a Node Readable
await ds.load((await fetch(url)).body!, { format: 'nt' });   // a Web ReadableStream
await ds.loadFiles(['a.nt', 'b.ttl'], { toGraph: g });        // parallel bulk path

const stream = ds.dump({ format: 'nq', compression: 'zstd' });   // ReadableStream<Uint8Array>
await pipeline(Readable.fromWeb(stream), fs.createWriteStream('out.nq.zst'));
await ds.dumpToFile('out.trig');                              // written by the engine
const text = await ds.dumpToString({ format: 'turtle' });
```

`load` takes a string, a `Uint8Array`, a Node.js `Readable`, a Web `ReadableStream`, any
async iterable of strings or bytes, or `{ path }`. It returns `{ inserted, receipt }`. A
load is one commit. The options are `format`, `baseIri`, `toGraph`, `compression`,
`lenient`, `signal`, `message` and, for CSV and TSV, the tabular options of
[C05](C05-tabular-imports.md). Formats and codecs are those of the Python package,
including Jena's TriX, RDF Thrift, RDF Protobuf and RDF/JSON. A path is read by the
engine, which is the fast path. Other inputs stream through a bounded channel (§5.2).

`dump` returns a Web `ReadableStream<Uint8Array>` at once and starts serializing when
the stream is first read. That stream type is the one Node.js, Bun, Deno and browsers
share, and `Readable.fromWeb` turns it into a Node.js stream. `dumpToFile` lets the
engine write the file and takes its format and codec from the name, as the Python
package's `dump` to a path does. A quad format writes every graph, and a triple format
writes the default graph or `fromGraph`.

The module also exports `parse(input, options)`, which yields quads without a dataset,
and `serialize(quads, options)`, which returns a byte stream.

### 3.7 Results as bytes

```ts
const body = await ds.queryToStream(q, { accept: 'application/sparql-results+json' });
return new Response(body, { headers: { 'content-type': body.contentType } });
```

`queryToStream` runs a query and serializes its results on the engine's threads, as the
server does, into SPARQL JSON, XML, CSV or TSV for SELECT and ASK, or any RDF format for
CONSTRUCT and DESCRIBE. No term object is created in JavaScript. This is the fast path
for a JavaScript web server that answers SPARQL requests from an embedded dataset.

### 3.8 History, reasoning, validation, search and stored queries

These wrap the same engine entry points as the Python methods of the same names, and
their options and reports are plain objects in the server's JSON shapes.

* **History.** `headCommit()`, `commits({ limit, before })`, `createSnapshot(name)`,
  `history()`, `setRetention({ keepCommits, keepAgeMs })` and `cloneTo(path, { at })`.
  The `at` option of the read methods takes a commit number, a `Date` or a string such
  as `snapshot:name`, `commit:42` or `time:<RFC 3339>`.
* **Reasoning.** `reason(profile, { rules })` materializes `rdfs`, `rdfs-simple` or
  `owl-rl`, or Jena rules, into `urn:x-sparkles:inferred` and resolves to a report.
  `clearInferences()` removes them.
* **Validation.** `validateShacl(shapes, { format, shapesGraph, dataGraph,
  includeInferred })` and `validateShex(schema, shapeMap, options)` resolve to reports
  whose results hold RDF/JS terms. `setWriteValidation(config)` installs a write guard.
* **Text, vector and geospatial search.** These work through SPARQL, as `text:query`,
  `spk:vectorSearch` and the GeoSPARQL functions, whenever the build has the feature and
  the dataset has the index. `enableText`, `createVectorIndex` and the rest of the index
  administration are methods with the Python names in camel case.
* **Stored queries.** `ds.storedQueries` has `list()`, `get(name, version?)`,
  `put(name, definition)` and `delete(name)`, over the catalog of
  [C16](C16-stored-queries.md) in `<db>/queries.json`, or in memory for an in-memory
  dataset. `ds.runStored(name, params, options)` binds the parameters through
  `stored::Definition::bind`, which checks their types, and runs the query like `query`.

### 3.9 The shared interface

```ts
interface SparqlDataset {
  query(q: string, o?: QueryOptions): Promise<QueryResult>;
  select(q: string, o?: QueryOptions): Promise<BindingsResult>;
  ask(q: string, o?: QueryOptions): Promise<boolean>;
  construct(q: string, o?: QueryOptions): Promise<QuadsResult>;
  update(u: string, o?: UpdateOptions): Promise<UpdateResult>;
  queryBindings(q: string, c?: QueryStringContext): Promise<Stream<Bindings>>;
  queryQuads(q: string, c?: QueryStringContext): Promise<Stream<Quad>>;
  queryBoolean(q: string, c?: QueryStringContext): Promise<boolean>;
  queryVoid(q: string, c?: QueryStringContext): Promise<void>;
}
```

The engine's `Dataset` and the client's `RemoteDataset` both implement it. The last four
methods are the `StringSparqlQueryable` interface of the RDF/JS query specification, so
tools written against that interface, which Comunica's engine also implements, accept a
Sparkles dataset. Options a remote server cannot honour, such as `at` on a server without
retained history, fail with the server's error.

## 4. Errors

The common package defines the error classes, and both packages throw them.

| Class | Thrown for |
|---|---|
| `SparklesError` | The root, extending `Error`, and errors without a narrower class. |
| `ParseError` | The root of syntax errors. |
| `SparqlSyntaxError` | `Error::SparqlSyntax`, with `line` and `column` when the parser gives them. |
| `RdfSyntaxError` | `Error::RdfParse`, and invalid rules, shapes and ShEx schemas. |
| `InvalidInputError` | `Error::Invalid`, a closed dataset or transaction, the wrong query form. |
| `UnsupportedError` | `Error::Unsupported`, a feature left out of the build, an operation an older server lacks. |
| `QueryTimeoutError` | `Error::Timeout`. |
| `CancelledError` | `Error::Cancelled` when no `AbortSignal` caused it. |
| `BudgetExceededError` | `Error::BudgetExceeded`, with `kind`, `limit` and `requested`. |
| `StorageError` | `Error::Corrupt`, `Poisoned` and `StorageFull`. |
| `DatasetLockedError` | A database directory held by another process. It extends `StorageError`. |
| `ConflictError` | `Error::Conflict`, `PreconditionFailed` and `WriterBusy`, and a write that would wait for its own transaction. |
| `NotFoundError` | `Error::NotFound` and `HistoryGone`. |
| `PermissionDeniedError` | `Error::NotPermitted`, and 401 and 403 from a server. |
| `ServiceError` | `Error::Service`. |
| `WriteRejectedError` | `Error::Rejected` and `GuardMissing`, with the validation report. |

Every error has a `code` string in Node.js's style, such as
`ERR_SPARKLES_SPARQL_SYNTAX`, so code can test it without importing the classes. An
`Error::Io` becomes a `SparklesError` with the `code`, `errno`, `syscall` and `path` of
the operating system error, such as `ENOENT`, which is what Node.js's own file functions
throw. A wrong argument type throws `TypeError`, and an invalid IRI or language tag
passed to the factory throws `InvalidInputError`.

An operation cancelled through its `signal` rejects with `signal.reason`, which is an
`AbortError` `DOMException` unless the caller gave another reason. That is how `fetch`
and Node.js's own APIs behave.

The native layer cannot construct JavaScript subclasses cheaply, so it throws a plain
`Error` with `code` and a JSON `details` property, and the TypeScript layer rethrows it
as the matching class. The client maps HTTP statuses and the server's error JSON onto the
same classes, as [P02 §4.6](P02-rust-client.md#46-errors-deadlines-and-cancellation)
does in Rust.

## 5. Threads and the event loop

### 5.1 Where work runs

The JavaScript thread does three things. It validates and converts arguments, it starts
work on another thread, and it turns finished batches into JavaScript objects. Everything
else runs on threads the addon owns.

The addon runs engine work on its own pool and not on libuv's thread pool. napi-rs's
`AsyncTask` would use libuv's pool, which has four threads by default and also serves the
file system, DNS lookups, `zlib` and `crypto`. A few long queries there would stall
unrelated I/O, and a write waiting for the writer lock would hold one of the four threads.
The addon instead uses napi-rs's Tokio integration. Each call is an `async fn` that
returns a promise. Its work runs on Tokio's blocking pool through `spawn_blocking`, and
the result comes back to the JavaScript thread through napi-rs's completion callback.

**Concurrent readers.** Reads run on snapshots, so any number may run at once and none
waits for a writer. The addon limits how many run at a time with a semaphore, so that a
burst of requests does not create hundreds of threads. The limit defaults to the number
of available cores and is set with `configure({ maxConcurrentQueries })`. Queries beyond
it wait in a queue without holding a thread. Lowering the limit takes back free permits
at once and the rest as running queries finish, so no query starts above the new limit. A streaming result takes a permit only while
it opens and while it computes a batch, and gives it back between pulls. An idle cursor
therefore keeps its snapshot but never blocks other queries. The engine's own parallel operators use
rayon's global pool, which is shared by all queries, as in the server.

### 5.2 Streams and backpressure

All data moves by pull, so a slow consumer slows the producer down and memory stays
bounded.

* **Query results.** The iterator holds one decoded batch. When it is half consumed, the
  TypeScript layer asks the addon for the next one, which is decoded on the pool while
  JavaScript reads the rest of the current batch. A consumer that stops reading leaves
  at most one batch prepared. napi-rs's `AsyncGenerator` support could serve the same
  purpose, but its documentation leaves overlapping `next()` calls to the implementer,
  and a batch interface in the TypeScript layer keeps native calls per batch rather
  than per row.
* **Quad patterns.** `match` reads 4096 index keys per batch, as `quads_for_pattern` does
  in Python, from one snapshot.
* **Loads from streams.** The TypeScript layer reads chunks from the input and hands
  them to the addon. The addon puts them in a channel of eight chunks, which a parser on
  the pool reads as a `std::io::Read`. The promise for a chunk resolves only when the
  channel has room, so the input is read no faster than the engine parses it.
* **Dumps and `queryToStream`.** The returned `ReadableStream` has a `pull` callback that
  asks the addon for the next chunk of about 64 KiB. The serializer runs on the pool and
  stops when the stream's queue is full.

ThreadsafeFunctions are used only where Rust calls JavaScript on its own schedule. These
are the `onProgress` callback of loads, compaction and index builds, and, in Phase 2, the
change feed's notifications. Each uses a bounded queue and drops intermediate progress
events when JavaScript falls behind, since only the latest matters. The `onProgress`
callbacks are deferred, as the Outcome records.

### 5.3 Cancellation

Every long operation takes `signal` and `timeout`. The addon gives each operation an
`Arc<AtomicBool>` as `QueryOptions::cancel`. The TypeScript layer listens for the
signal's `abort` event and sets the flag through a native call. The engine checks the
flag in its operators and stops with `Error::Cancelled`, and the binding rejects with
`signal.reason`. An operation still waiting in a queue for the pool or the writer is
removed from the queue. napi-rs's own `AbortSignal` support for `AsyncTask` cannot stop a
task once it has started, which is why the binding uses the engine's flag.

An abandoned iterator, one left by `break` or an exception in a `for await` loop, calls
`return()`, which releases its batch and the result table at once.

### 5.4 Transactions and the single writer

The engine has one writer per dataset. Its write transaction holds a lock guard that must
stay on the thread that took it. The Python package runs each transaction on a thread of
its own that owns the guard and receives operations over a channel, and the Node.js
package does the same with three additions for the event loop.

1. **Waiting for the writer holds no thread.** Each dataset has an asynchronous FIFO
   queue of writers in the addon. A write or transaction first waits in that queue as a
   pending promise. Only when it reaches the front does a pool thread take the engine's
   writer lock, which is then free. One-shot writes, such as `add`, `update` and `load`,
   go through the same queue, so they are served in arrival order.
2. **Each `tx` method is a message.** `tx.add` sends a request to the transaction's
   thread and returns a promise for the answer. Between messages the thread waits on its
   channel and the JavaScript thread is free. `tx.match` and `tx.select` return their
   results in batches, like the dataset's methods.
3. **A callback cannot deadlock on its own transaction.** A write on the dataset from
   inside the callback would wait in the queue behind the transaction that is waiting for
   the callback. The binding runs the callback inside an `AsyncLocalStorage` context that
   names the transaction, and every write on the dataset checks it. A write made in that
   context throws `ConflictError` with a message that points to `tx`. Writes from other
   asynchronous flows wait in the queue as usual. `AsyncLocalStorage` exists in Node.js,
   Bun and Deno.

A transaction holds the writer for as long as its callback runs, including while the
callback awaits network calls or timers. The `timeout` option bounds that time. When it
expires, or the signal aborts, the binding marks the transaction aborted, cancels the
operation in progress, rejects every later `tx` call, and rolls back when the callback
settles. The writer is free as soon as the rollback ends, even if the callback never
settles. The usage guide will tell readers to do slow I/O before the transaction starts.

An update in a transaction that fails after it began to change data aborts the
transaction, as in Python, because the engine has no savepoints. A syntax error does not.

### 5.5 Memory and budgets

* A SELECT result costs 8 bytes per cell in the engine until the iterator is done or
  abandoned, because the engine produces the whole table of ids first. The decoded batch
  adds its terms' text. `maxRows`, `maxMemoryBytes` and `maxRowsProduced` bound the
  engine's side as in the server.
* `configure({ batchBytes })` bounds the size of a decoded batch. The default of 1 MiB
  keeps the batches of 64 concurrent iterators under 128 MiB including prefetch.
* Term objects are ordinary JavaScript objects that the garbage collector frees. The
  addon's memory shows in `process.memoryUsage().rss` and not in the V8 heap, and the
  usage guide will say so. `ds.stats()` reports the engine's caches, as `sparkles stats`
  does.
* The block cache and the other engine caches are per store, and the store is shared by
  all handles in the process (§3.1). The cache sizes are options of `Dataset.open`.

## 6. Terms and the boundary

### 6.1 The term model

The common package exports classes that implement the `@rdfjs/types` interfaces, and a
`factory` object that is an RDF/JS `DataFactory`.

| RDF/JS | Sparkles class | Notes |
|---|---|---|
| `NamedNode` | `NamedNode` | The factory validates the IRI. |
| `BlankNode` | `BlankNode` | `factory.blankNode()` makes a fresh label. |
| `Literal` | `Literal` | `language`, `direction` (`'ltr'`, `'rtl'` or `''`) and `datatype`. |
| `Variable` | `Variable` | For bindings and query results. |
| `DefaultGraph` | `DefaultGraph` | A singleton. |
| `Quad` | `Quad` | Also an RDF 1.2 triple term (§6.4). |

`equals` follows the specification. Two literals are equal when their value, language,
direction and datatype are equal, so `equals` compares the lexical form and not the
value. `factory.literal(value, languageOrDatatype)` takes a language string, a datatype
or a `DirectionalLanguage` object, as `@rdfjs/types` 2.x declares. `fromTerm` and
`fromQuad` copy foreign terms. Each term also has `toString()`, which returns its
N-Triples form.

The common package adds conversions between literals and JavaScript values.

| JavaScript value | Literal datatype | `literal.toJs()` returns |
|---|---|---|
| `string` | `xsd:string` | `string` |
| `boolean` | `xsd:boolean` | `boolean` |
| `number`, an integer | `xsd:integer` | `number` when it is a safe integer, else `bigint` |
| `number`, otherwise | `xsd:double` | `number`, also for `xsd:float` |
| `bigint` | `xsd:integer` | as above |
| `Date` | `xsd:dateTime` | `Date` |
| `Uint8Array` | `xsd:base64Binary` | `Uint8Array`, also for `xsd:hexBinary` |

`xsd:decimal` has no native JavaScript type, so `toJs()` returns its lexical form, as for
every other datatype and for ill-typed literals. `factory.fromJs(value)` makes a literal
from a value.

Every method that takes a term accepts any object with the RDF/JS shape, checked by
`termType` and `value`, and reads `language`, `direction` and `datatype` from literals
and the four positions from quads. Terms from N3.js, rdf-ext or Oxigraph's package work
without conversion.

### 6.2 Crossing the boundary

Creating a JavaScript object for every term of every row is the main cost of the
binding. The Python package keeps the result table and decodes one row at a time. In
Node.js, every native call has a fixed cost on the JavaScript thread, so the binding
decodes in batches on the pool and hands each batch over in one call.

A batch holds up to `batchSize` rows, 1024 by default, or `batchBytes` of term text,
whichever comes first. Its encoding is compact.

* **A term dictionary.** Each distinct term of the batch appears once, keyed by its
  engine id, so a predicate or class that repeats in every row is decoded once. The
  dictionary is one UTF-8 buffer of term text with an offsets array, a kind byte per
  term, and references to the datatype and language entries of literals.
* **The cells.** A `Uint32Array` with one entry per cell in row order. Zero means
  unbound, and any other value is an index into the dictionary.

The batch reaches JavaScript as one external `ArrayBuffer` that the addon allocated, so
nothing is copied. The TypeScript layer creates term objects lazily. A row's `get`
decodes a dictionary entry the first time any row asks for it and caches the object for
the rest of the batch. A consumer that reads one column of a wide result never pays for
the others, and one that only counts rows creates no terms at all.

The alternative is to create JavaScript strings in the addon with
`napi_create_string_utf8` while the batch is resolved, which costs time on the JavaScript
thread for every distinct term, used or not. Phase 1 builds the lazy form and measures
both on the benchmark of §11. Open question 2 records the choice.

Quads from `match` and `construct` use the same encoding with four columns. Inputs go the
other way as arrays of terms, which `addAll` sends to the addon in chunks of 4096 quads.

### 6.3 Other data factories

The `factory` option of the read methods makes results with another RDF/JS factory, such
as N3.js's `DataFactory` or rdf-ext's environment. The binding then calls the factory for
each term it decodes, which costs one call per distinct term per batch. Without the
option, results use the common package's classes, which already satisfy every RDF/JS
consumer.

### 6.4 Triple terms

RDF 1.2 allows a triple as the object of another triple. RDF/JS represents it as a
`Quad` whose graph is the default graph, and `@rdfjs/types` allows a `Quad` in the
subject and object positions. The binding maps a `Quad` term in the object position to
the engine's triple term and back. A `Quad` term in the subject position, which RDF-star
allowed and RDF 1.2 does not, throws `InvalidInputError`, and so does a quoted quad
whose graph is not the default graph. N3.js can parse Turtle-star with quoted subjects,
and such data has to be rewritten with reifiers before it is loaded.

## 8. The remote client

### 8.1 API

```ts
import { SparklesClient } from '@sparkles-rdf/client';

const client = new SparklesClient('https://db.example.org', { token, fetch });
const books = client.dataset('books');               // a RemoteDataset
for await (const row of await books.select('SELECT ?t WHERE { ?b <urn:title> ?t }')) { … }
const { receipt } = await books.update('INSERT DATA { … }', { message: 'fix titles' });
await books.graphs.put(g, turtle, { contentType: 'text/turtle', ifMatch: etag });
const res = await client.api.GET('/$/datasets/{name}', { params: { path: { name: 'books' } } });

const endpoint = SparklesClient.endpoint('https://query.wikidata.org/sparql');  // any SPARQL server
```

The client follows the Rust client of [P02](P02-rust-client.md) in what it does and how
it names it, in TypeScript's conventions.

* **Queries** send the SPARQL protocol with POST, read SPARQL JSON results with a
  streaming parser so that rows arrive while the response downloads, and yield the same
  `Bindings` and `Quad` objects as the engine. CONSTRUCT results are read as N-Triples
  or N-Quads, line by line.
* **Updates and Graph Store writes** resolve to receipts read from the response, as
  [P02 §4.3](P02-rust-client.md#43-updates-and-receipts) describes. `batch()` collects
  operations into one update request, which the server runs as one commit. There are no
  multi-request transactions, because the server has none.
* **The admin API** is reached through `client.api`, a typed `fetch` wrapper built with
  openapi-fetch over the generated `paths` type. Every route of the OpenAPI description
  is callable with typed parameters and bodies. The hand-written methods cover the SPARQL
  protocol, the Graph Store Protocol, uploads, commits, history and stored queries,
  where streaming or receipts need more than the generated types.
* **Authentication** takes a bearer token, Basic credentials, or the browser's cookies
  with `credentials: 'include'`, in which case the client sends the CSRF header that the
  server requires for cookie sessions, as the UI does.
* **Retries** repeat idempotent requests on 429 and 503 with `Retry-After`, as P02 §4.8
  does, and never repeat an update.
* **Cancellation** passes the `signal` to `fetch`.
* **Plain endpoints.** `SparklesClient.endpoint(url)` talks to any SPARQL 1.1 server and
  offers only the protocol operations.

### 8.2 Generated types

openapi-typescript turns `docs/openapi.json` into `paths` and `components` types. X03's
Phase 2, which would describe the remaining admin bodies field by field, was not built,
so some responses are typed as plain objects in the description. The client keeps hand
types for those, starting from the types in `ui/src/lib/api.ts`, and a test checks each
hand type against its schema wherever the schema has fields. When X03's Phase 2 lands,
the hand types are replaced with the generated ones.

### 8.3 The UI's client

`ui/src/lib/api.ts` mixes the HTTP calls with things that belong to the UI, such as
formatting helpers, upload forms and clone dialogs. The client package takes over its
transport and types. The UI can then import them and keep its own helpers, which removes
the duplicated types. Phase 1 builds the client package without changing the UI. The
migration is open question 6.

### 8.4 Size

The client and common packages together should stay under 30 KB minified and 10 KB
compressed, without the generated types, which are erased at compile time. They have
one runtime dependency, openapi-fetch, which is about 6 KB.

## 9. Interoperability

### 9.1 N3.js

```ts
import { Parser, Store, Writer } from 'n3';

await ds.addAll(new Parser().parse(turtleText));          // N3.js quads go in unchanged
const store = new Store();
for await (const q of ds.match(null, rdfType, person)) store.addQuad(q);
new Writer().addQuads(await ds.match(alice).toArray());    // Sparkles terms are RDF/JS terms
```

N3.js's `StreamParser` is a Node.js object stream of quads, so it can feed `addAll`
directly, and `match().toStream()` can feed N3.js's `StreamWriter`.

### 9.2 Comunica

```ts
import { QueryEngine } from '@comunica/query-sparql-rdfjs';

const engine = new QueryEngine();
const bindings = await engine.queryBindings(query, { sources: [ds.source()] });
```

`ds.source()` returns an object that implements the RDF/JS `Source` interface. Its
`match` returns an RDF/JS `Stream` of quads from one snapshot, read in batches. It also
has `countQuads`, which Comunica uses for its join order when a source provides it. It
returns the exact count from `Snapshot::count` when the bound positions form a prefix of
one of the index permutations, and the index's estimate otherwise. That needs a small
additive API in `crates/sparkles`, `Dataset::count_pattern`. In Phase 2, `ds.store()`
also implements the RDF/JS `Store` interface (`import`, `remove`, `removeMatches` and
`deleteGraph`), which Comunica needs to run updates against a source.

Comunica over `ds.source()` evaluates joins in JavaScript, one quad pattern at a time,
and creates a term object for every intermediate quad. Sparkles' own engine evaluates the
same query over integer ids with its optimizer and returns only the final rows. For a
query over Sparkles data alone, `ds.select` should be faster by one to two orders of
magnitude on the benchmark of §11, and the usage guide will say to prefer it. Comunica is
the right tool when one query joins Sparkles data with other sources, such as remote
SPARQL endpoints, Linked Data documents, Solid pods or files. A Sparkles server can also
be a Comunica source by its SPARQL endpoint URL, with no package involved.

### 9.3 rdf-ext and other RDF/JS libraries

rdf-ext's datasets and N3.js's store accept Sparkles terms, and Sparkles accepts theirs.
`await ds.match(...).toArray()` gives an array that `rdf.dataset(quads)` takes. Libraries
that need a synchronous `DatasetCore`, such as clownface and the JavaScript SHACL
validators, work on such a copy. Open question 3 asks whether the package should offer a
synchronous read-only view instead.

* Phase 2 takes two to three weeks, most of it in the platform jobs, the Comunica source

## 11. Performance targets and benchmark

### 11.1 Targets

The targets are for the benchmark data of `scripts/bench.sh` at 1.05 million triples, on
the benchmark machine, with nothing else running.

* **T1, call overhead.** A trivial `ask` resolves in 30 µs or less at the median. The
  Python package measured 14 to 20 µs for the same call.
* **T2, row throughput.** Iterating `export-500k` (500,000 rows of three terms) with every
  term materialized runs at one million rows per second or more. Counting the rows
  without reading terms runs at three million rows per second or more.
* **T3, query suite.** For every query of the suite, the time from the call to the last
  row is at most 1.25 times the Rust library's time for the same query, and lower than
  Oxigraph's JavaScript package's time, except where both take under one millisecond.
* **T4, loads.** Loading the N-Triples file by path reaches 90% of `sparkles load`'s
  throughput, and loading it from a Node.js `Readable` reaches 60%.
* **T5, the event loop.** While eight queries of the suite run concurrently for ten
  seconds, `perf_hooks.monitorEventLoopDelay` reports a 99th percentile delay under 5 ms.
* **T6, memory.** An open iterator costs at most two batches over the engine's own
  result memory.
* **T7, concurrency.** Eight concurrent `star-join` loops in one process reach 80% of the
  throughput that `oha` measures against `sparkles serve` with eight connections on the
  same machine.

### 11.2 Benchmark plan

`scripts/bench-js.mjs` runs each engine alone, as `bench.sh` does for servers, and
writes JSON and Markdown results next to the others. It loads `data.nt` from
`scripts/gen-data.py` into each engine and runs the queries of `bench.sh` with two warm-up
runs and ten timed runs, reporting the median and the 95th percentile.

* **Sparkles.** The engine package on Node.js 24, from an in-memory dataset and from a
  persistent one, with all terms materialized. A second column uses `queryToStream`
  with TSV, which shows the cost of term objects.
* **Oxigraph's JavaScript package.** Its in-memory `Store`, loaded from the same file,
  queried through `query`, whose results arrive as an array of `Map`s.
* **N3.js with Comunica.** An N3.js `Store` queried through
  `@comunica/query-sparql-rdfjs`. Queries that run over a time limit of 60 seconds are
  reported as timeouts.
* **Quad patterns.** `match` with one, two and three bound positions against N3.js's
  `Store.match` and Oxigraph's `Store.match`, iterated to the end.
* **Bun.** In Phase 2, the Sparkles column again on Bun.

Before timing, each engine's answer to each query is fingerprinted and compared, as
`scripts/bench-answers.py` does for the servers, and an engine that disagrees is
footnoted and not ranked. The peak resident memory of each engine's process is reported
with the tradeoff stated. Sparkles keeps its block cache and its result tables in memory
for speed, while Oxigraph's and N3.js's stores hold every quad as JavaScript or
WebAssembly data.

## 12. In the browser

This section documents what a browser build of the engine would take. Nothing in it is
committed to. The recommended path for browsers is the client package against a server.

### 12.1 The client in the browser

The client package needs only `fetch`, Web Streams and `TextDecoder`, which every current
browser has. It uses the server's CORS support, cookie sessions with the CSRF header or
bearer tokens, and streams results as they arrive. It adds no WebAssembly download, works
with datasets of any size, and keeps the data on the server where access control applies.
This is the right choice for almost every web application.

### 12.2 What the engine needs from its platform

| Dependency | Use in the engine | In a browser |
|---|---|---|
| Memory-mapped files (memmap2) | Index generations, vocabularies and the text, vector and spatial indexes are read through mapped files. An in-memory dataset also builds each new generation in a temporary directory and maps it. | No mapping and no file system on `wasm32-unknown-unknown`. Generations would have to live in heap buffers behind the same block-reading interface. |
| A write-ahead log with fsync | Durability of persistent datasets. | No fsync. An in-memory variant needs no log. |
| Temporary files | The index builder's external sort spills runs to disk, and compaction writes into a directory. | Runs would have to stay in memory, which bounds the data by the WebAssembly heap. |
| rayon | Parallel sorts in the builder, and parallel operators in queries and validation. | No threads in `wasm32-unknown-unknown`. A `parallel` cargo feature would turn the parallel loops into sequential ones, as the formatter's browser build does. Threads would need wasm threads with `SharedArrayBuffer`, which needs cross-origin isolation. |
| Tokio (`rt`, `sync`) | The commit watch channel, and DNS lookups for the outbound policy. | The `sync` parts compile. The runtime and the lookups do not. |
| reqwest | SERVICE and `LOAD <http…>`. | reqwest has a `fetch` backend, but it is asynchronous and the engine's evaluator is synchronous. SERVICE would be unsupported, or would run only in a worker that blocks on `Atomics.wait` while another worker fetches. |
| `std::time` | Commit times, timeouts and budgets. | `SystemTime::now` and `Instant::now` panic on `wasm32-unknown-unknown`. The engine would need a time shim over `Date.now` and `performance.now`. |
| getrandom | Blank node labels and dataset ids. | Works with the `wasm_js` backend, as in the formatter's build. |
| stacker | Growing the stack for deeply nested queries. | It cannot grow the stack in WebAssembly. Deep queries would need a larger fixed stack and the depth limits that `sparql/depth.rs` already enforces. |
| Tantivy | Full-text search. | Tantivy relies on mapped files and threads. The `text` feature would be off. |
| zstd | zstd inputs and dumps, through the C library. | The C build for WebAssembly needs a clang toolchain. The feature would be off, leaving gzip, brotli and LZ4, which are pure Rust. |
| mimalloc | The server's allocator. | Not used. The library is allocator-neutral, and WebAssembly uses the default allocator. |
| libc `statvfs` | Free disk space checks. | Already limited to Unix targets. |

The geospatial crates, the parsers and serializers, the SPARQL engine itself, the
reasoner, the SHACL and ShEx validators and ICU's normalizer are pure Rust and should
compile. ICU's compiled data adds to the size.

### 12.3 How Oxigraph does it

Oxigraph's JavaScript package is a WebAssembly build of its engine with an in-memory
store only. Its documentation says so, and its `Store` has no persistence. Version
0.5.11 ships one module for Node.js and one for bundlers and browsers, each about 4 MB
uncompressed. All of its methods are synchronous and run on the calling thread, so a
long query blocks the page or the event loop, and `match` and `query` return arrays
rather than streams. It needs WebAssembly reference types and `WeakRef`, and a bundler
that handles WebAssembly. That design keeps the build simple, with no threads, no files
and no asynchronous storage, at the cost of persistence, parallelism and responsiveness.

### 12.4 A WebAssembly build of Sparkles

A build for browsers would need these changes, in this order.

1. **An in-memory engine without files.** A storage backend that keeps generations,
   vocabularies and deltas in heap buffers, used by the in-memory store on every target.
   Compaction would build into memory. This is the largest change, because the reader
   and builder assume files today.
2. **Platform shims.** A time source, a `parallel` feature that makes rayon optional,
   SERVICE and remote LOAD disabled with `UnsupportedError`, and `text` and `zstd` off.
3. **Packaging.** Two routes exist. napi-rs can compile the same crate to
   `wasm32-wasip1-threads` and publish it as a fallback package that runs in browsers
   through `@napi-rs/wasm-runtime`. That reuses the binding code, but it needs
   `SharedArrayBuffer`, so every page that uses it must send the
   `Cross-Origin-Opener-Policy` and `Cross-Origin-Embedder-Policy` headers. A
   `wasm-bindgen` build for `wasm32-unknown-unknown`, single-threaded, works on any page
   but needs its own thin binding over the same TypeScript layer. Open question 8 asks
   for a spike that compares them.
4. **Running off the page's thread.** The engine would run in a dedicated worker, and the
   TypeScript layer would talk to it through messages, so that the API stays
   asynchronous and the page stays responsive.
5. **Size.** The native module of the Python package is 25 MB, and Tantivy and the C
   codecs account for part of it. A browser build without `text` and `zstd`, built for
   size with `wasm-opt`, should aim at 8 MB uncompressed and 3 MB with brotli, about
   twice Oxigraph's module, because Sparkles adds the reasoner, the validators and
   GeoSPARQL. Feature flags could cut it further.
6. **Persistence, optionally.** The Origin Private File System offers synchronous file
   handles (`FileSystemSyncAccessHandle`) in dedicated workers, with `flush` as the
   equivalent of fsync. A persistent browser store could keep its generation files and
   log there with little change to the engine's design, once step 1 has abstracted the
   storage. IndexedDB is asynchronous only, so it suits whole-dataset snapshots, such as
   a dump after each commit, better than a log. The simplest first version leaves
   persistence to the application through `dump` and `load`.

The engine would still face the WebAssembly heap limit of 4 GB, and browsers often grant
less. With Sparkles' compact ids that is room for tens of millions of triples, which is
far more than a page should download.

The effort is six to ten weeks for steps 1 to 5 and three to four more for step 6. Step 1
is useful beyond the browser, because it would remove the temporary directory that
in-memory datasets use today.

## 13. Acceptance examples

* **A1.** `Dataset.memory()` is empty. After
  `await ds.load('<urn:s> <urn:p> "x" .', { format: 'nt' })`, `await ds.count()` is 1 and
  `await ds.has(factory.quad(s, p, factory.literal('x')))` is true.
* **A2.** `await ds.load({ path: 'data.ttl.gz' })` loads the same quads as the
  uncompressed file, and so does `ds.load(fs.createReadStream('data.ttl.gz'), { format:
  'turtle' })`.
* **A3.** A persistent dataset written, closed and reopened has the same quads. A second
  process that opens the directory gets `DatasetLockedError`. A `worker_threads` worker
  that opens it while the main thread has it open gets a working handle on the same store
  and sees the main thread's commits.
* **A4.** `await ds.select('SELECT ?s ?o WHERE { ?s ?p ?o } ORDER BY ?o')` has `size`
  equal to the number of rows, and each row's `get('o')`, `get(factory.variable('o'))`
  and `toObject().o` are equal literals. An unbound OPTIONAL variable is `undefined`.
* **A5.** `ds.query('SELECT * WHERE {')` rejects with a `SparqlSyntaxError` that is also
  a `SparklesError` and has `code` `ERR_SPARKLES_SPARQL_SYNTAX`. Loading a missing path
  rejects with `code` `ENOENT`. `ds.select('ASK {}')` rejects with `InvalidInputError`.
* **A6.** `(await ds.update('INSERT DATA { <urn:s> <urn:q> 1 }')).inserted` is 1, and its
  `receipt.commit.seq` is one more than the previous head. A second identical update has
  `receipt.committed` false.
* **A7.** In `ds.transaction(async tx => …)`, a quad added through `tx` is found by
  `tx.match` and not by `ds.match` until the promise resolves. A callback that throws
  leaves no change. `ds.add` inside the callback rejects with `ConflictError`, while an
  `ds.add` started elsewhere during the transaction resolves after it.
* **A8.** A transaction whose callback awaits a promise that never settles is rolled back
  when its `timeout` expires, and a later `ds.add` succeeds.
* **A9.** Aborting the `signal` of a query that runs for seconds rejects it within 100 ms
  with the signal's reason, and the pool runs the next query at once.
* **A10.** During a ten-second query on the pool, a `setInterval` of 1 ms keeps firing
  with no gap over 5 ms.
* **A11.** Iterating a SELECT over 100,000 rows with `break` after ten rows releases the
  result, and the process's resident memory returns to within 10% of its level before
  the query.
* **A12.** A directional literal, `factory.literal('x', { language: 'ar', direction:
  'rtl' })`, and a triple term in the object position round-trip through a dataset with
  `equals` true. A triple term in the subject position rejects with `InvalidInputError`.
* **A13.** Quads parsed by N3.js's `Parser` load through `addAll`, and N3.js's `Writer`
  writes quads from `ds.match`. Comunica's `@comunica/query-sparql-rdfjs` over
  `ds.source()` answers `star-join` with the same rows as `ds.select`.
* **A14.** `ds.dump({ format: 'nq' })` read to the end loads into a new dataset with the
  same quads, and a consumer that reads one chunk and waits leaves the serializer
  paused.
* **A15.** The same test file, written against `SparqlDataset`, passes against an
  embedded `Dataset` and against a `RemoteDataset` on a `sparkles serve` started by the
  test.
* **A16.** `client:check` passes on the committed `openapi.d.ts`, and fails after a
  route is added to the server without regenerating it.
* **A17.** The packed packages install with npm and pnpm into an empty project on each
  Phase 1 platform, and the suite passes on Node.js 22, 24 and 26.

## 14. Rejected alternatives

* **A WebAssembly package as the main server-side engine.** Oxigraph took this route for
  JavaScript. For Sparkles it would give up persistent datasets, because WebAssembly has
  no mapped files and no fsync, and it would give up parallel query operators and the
  bulk loader's threads. It would run on the JavaScript thread unless wrapped in workers,
  it would be limited to a 4 GB heap, and WebAssembly generally runs slower than the
  same code compiled natively. A native addon keeps everything the server has. A
  WebAssembly build stays an option for the browser (§12.4).
* **Neon instead of napi-rs.** Neon is mature and also builds on Node-API. napi-rs
  generates the TypeScript declarations from the Rust code, has a CLI that builds and
  publishes the per-platform packages as optional dependencies, supports Tokio-backed
  `async fn`, async iterators and Web streams, and can target WebAssembly from the same
  crate. With Neon the binding would have to write and keep these by hand.
* **Only an HTTP client.** It would make every JavaScript user run a server, including
  tests, command-line tools, desktop applications and functions that ship their data.
  Every result would also pay for serialization and parsing. The client is still built,
  as the path for browsers and remote servers.
* **UniFFI's JavaScript support.** UniFFI, which the JVM bindings of [P04](P04-jvm-bindings.md) use, has
  no official JavaScript backend. The third-party uniffi-bindgen-react-native project has
  a Node-API runtime in pre-release versions. Using it would share interface definitions
  with the JVM bindings, but it passes arguments through serialized buffers, has no
  notion of RDF/JS terms, async iterators with backpressure or Web streams, and is not
  yet stable. It may be worth revisiting once the JVM bindings have settled.
* **Running engine work on libuv's thread pool.** napi-rs's `AsyncTask` is the simplest
  way to run work off the JavaScript thread, but the pool is small and shared with file
  and network I/O (§5.1).
* **A `Dataset` that implements RDF/JS `DatasetCore`.** `DatasetCore` is synchronous.
  `add` and `delete` would commit on the JavaScript thread, with an fsync each, and
  `match` would read the index there. Open question 3 keeps a read-only variant open.
* **Calling a C ABI through Node.js FFI libraries.** Libraries such as koffi call C
  functions without a compiled addon, but each call is synchronous on the JavaScript
  thread and every value is marshalled by hand.
* **A push-based result stream with ThreadsafeFunctions.** Rows pushed from a Rust thread
  through a ThreadsafeFunction would need their own flow control and would queue on the
  event loop. Pulled batches give backpressure for free (§5.2).

## 15. Open questions

1. **Package names.** `@sparkles-rdf/*` is a placeholder until the npm scope is
   registered. Default: `@sparkles-rdf/engine`, `@sparkles-rdf/client` and
   `@sparkles-rdf/common`.
2. **Batch decoding.** Lazy decoding in JavaScript from one buffer, or eager JavaScript
   strings made by the addon. Default: lazy, unless the Phase 1 benchmark shows eager
   decoding faster on `export-500k` with all terms read.
3. **A synchronous read-only view.** Libraries such as clownface and the JavaScript
   SHACL validators need a synchronous `DatasetCore`. A view over one snapshot could
   answer `has`, `match` and `size` synchronously, at the cost of reading the index on
   the JavaScript thread, where a page fault on a mapped file blocks the event loop.
   Default: not in Phase 1. Measure how long such reads block on a cold cache first.
4. **The addon's allocator.** mimalloc as the addon's global allocator affects only the
   addon. Default: the system allocator, with mimalloc for the musl packages if the
   Phase 2 benchmark on Alpine shows a clear gain.
5. **A default transaction timeout.** A forgotten `await` can hold the writer for good.
   Default: no timeout, and a warning through `process.emitWarning` when a transaction
   holds the writer for more than 30 seconds.
6. **The UI on the client package.** Default: move the UI's transport and types onto
   the client in Phase 2, keeping the UI's helpers in the UI.
7. **Windows on arm64 and FreeBSD.** napi-rs supports both targets. Default: add them
   when a user asks, since the engine is not tested there.
8. **The WebAssembly route.** napi-rs's WASI target or a `wasm-bindgen` build (§12.4).
   Default: decide with a one-week spike at the start of Phase 3, if Phase 3 starts.
9. **Blank node labels across writes.** As in Python, a label that the engine did not
   hand out names a new node in each write. Default: follow the Rust API and document
   it.

## Outcome

The workspace now builds `@sparkles-rdf/common`, `@sparkles-rdf/engine` and
`@sparkles-rdf/client`. The engine uses a separate Node-API Cargo workspace and
keeps JavaScript handles local to their environment. Rust-only persistent store
sharing supports aliases and workers; transaction ownership checks reject unsafe
snapshot capture and writes from an active callback. Queued writers preserve FIFO
order and cancellation, and closing datasets terminates transactions, results,
loads, dumps and commit-feed waits.

Queries use pull-driven batches and lazy RDF/JS term decoding. Receipts and count
fields use lossless `bigint`; common terms accept foreign RDF/JS factories,
directional literals and RDF 1.2 triple terms. Loads/dumps and standalone
parse/serialize use bounded queues, backpressure and stream cancellation. Catalog
and repository handles expose lifecycle-aware dataset and backup operations.
History, snapshots, branches/merges, stored queries, settings, schema, GraphQL,
validation, reasoning and indexes have concrete administration methods. RDF/JS
Source and Store adapters support Comunica queries and updates, and change feeds
wait for engine commit notifications. The vector embedding executor uses a bounded
`waitMs` argument rather than advertising an abort control the underlying executor
cannot honor.

Platform package manifests and gated CI cover Linux glibc/musl x64/arm64, macOS
x64/arm64 and Windows x64 MSVC, testing Node 22/24/26 plus Bun and Deno. Installed
archive checks exercise runtime loading and strict TypeScript declarations, including
the typed OpenAPI client. Local execution is on Linux x64 glibc; other native targets
are configured for CI and have not been executed locally. No npm publication occurred.

All 162 entries of the original administration mapping now have concrete Node
decisions. Catalog reservation and backup-file plumbing, policy/retention runners,
fixed repository registries, schedule previews, formatter/linter, geometry conversion,
RDF syntax checking, SPARQL parsing and IRI/language-tag checking are implemented.
Policy execution shares dataset writer admission and rejects transaction-owner
captures; controls unsupported by retention are rejected before mutation. The newer
Rust branch-relink operation remains an explicit binding follow-up. The optional
browser/Wasm engine and UI transport migration remain deferred.
The comparative performance harness and publication gate also remain follow-up work.

`configure({ maxConcurrentQueries })` sets the number of queries that may run at once,
and queries already running keep the permits of the old limit until they finish. A
streaming result holds a reader permit only while it opens and while it computes a batch,
and a `queryToStream` producer gives its permit back while it waits for the reader. An
open cursor keeps its snapshot until it is drained, closed or collected, so callers that
stop reading early should call `close()` or use `await using`. The result iterator asks
for the next batch once half of the current batch has been consumed. Dumps and
`queryToStream` serialize on Tokio's blocking pool. `catalog.reserve()` returns a promise,
because a claim can touch the catalog's files. A panic inside the addon reaches
JavaScript as an `InternalError` rather than as invalid input.

The remote client sends its configured credentials only to the server's origin and to
the origins of a plain endpoint's update and Graph Store URLs. An absolute URL from a
server response, such as a page's `next` link, does not receive them. Dataset names `.`
and `..` are rejected, because they would normalize onto another path. The real-server
client test runs in `mise run node:test` and in the Linux x64 job of the Node workflow.

The `onProgress` callbacks of §5.2 are deferred. Loads have no progress hook in the
engine, so they need engine work before a ThreadsafeFunction can report anything, and
compaction alone did not justify a separate callback path in the binding.

**Release platforms (2026-10-09).** The release workflows now build only for Linux on
x86_64 and arm64 and for macOS on Apple silicon, on Namespace runners. The Windows and
Intel macOS jobs were removed to keep CI time down. The code paths for those platforms
remain, and they come back by adding their jobs again.

**Fine-grained calls (2026-10-09).** The binding comparison of `mise run
bench:bindings` found the per-call APIs far slower than N3.js's `Store`, while queries
were faster than both incumbents. A `has()` or a small `match` made three or four
round trips through the addon's pool, each of which costs tens of microseconds, and a
quad crossed as one JSON object that JavaScript decoded term by term. Three changes
followed.

* The call that makes a result also computes its first batch, which `takeFirst` hands
  to JavaScript. A batch that drains a scan or a materialized result says so and frees
  the rows, so the iterator neither prefetches nor closes it natively.
* A quad crosses as four cells that index the batch's terms, so a term shared by many
  quads is sent and decoded once per batch. The iterator hands out an item it has
  already decoded at once when no earlier `next()` is pending.
* On a dataset in memory, `match` (and so `has`) runs the scan and a first batch of up
  to 16 quads on the JavaScript thread, which takes a few microseconds and so stays
  within §1's rule for the event loop. Later batches, datasets on disk and transactions
  use the pool as before.

In an A/B/B/A comparison on a busy laptop at 105,000 triples, `has()` went from about
206 to 19 µs per probe, the first match of `(s p ?)` from 232 to 25 µs, `(s ? ?)` from
390 to 50 µs per subject, and iterating every quad from 1.0 s to 0.30 s. These figures
are directional, and a quiet-machine run of the comparison is the authority. Single
adds in a transaction were unchanged at about 100 µs, because each crosses to the
transaction's worker thread through the pool.
