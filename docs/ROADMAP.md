# Roadmap

This roadmap prioritizes correctness, standards conformance, performance, robustness
and the standard features expected of a graph database.
Embedded agent memory and entity representation follow, and applications built on top of
Sparkles, such as the supply-chain pilot, come after them. New features enter the delivery
path when a concrete use case or an adopted dependency requires them. A separate analyst
workbench follows these goals.

Existing storage, query, reasoning, search, security and recovery capabilities retain
their required phases and acceptance gates. Close competitive results can be accepted
with their measurements and tradeoffs recorded. Packaging, recovery, installed-artifact
testing and the API compatibility contract advance alongside capability completion.

The [feature index](FEATURES.md) and its category guides describe what Sparkles does
and does not do today. Every known gap names the roadmap item that addresses it.
[BENCHMARKS.md](BENCHMARKS.md#where-sparkles-loses) records the measured results and the
workloads where Sparkles loses. The tiers list remaining work, followed by a record of
completed items.

The current priorities are engine correctness, performance and standard features in
Waves A and A2, followed by embedded agent memory and the ontology platform, including its
editor, in Waves B and C, which run alongside them. Shared entity representation follows
memory. Packaging, recovery and the API compatibility contract advance alongside capability
completion. The [delivery priorities](#delivery-priorities) explain their dependencies.
The numbered tiers are the detailed backlog, and [Completed](#completed) records finished
items.

## How the roadmap is organized

The work is grouped into seven tiers. Complete the adopted requirements of partial
capabilities and the selected release contracts before unrelated new breadth, including
requirements whose follow-ups appear in a lower tier. The tiers order eligible phases
and extensions by effort, dependencies and impact on the goals above. Independent phases
can run in parallel. A deferred adopted requirement keeps its parent capability partial.

Each item has a number that stays fixed for its lifetime. Specs, FEATURES and code
comments refer to items by these numbers, so a number is never reused or changed. The
numbers are not a ranking, and a new item takes the next free number whatever its tier.

Implementation status is recorded in the [capability matrix](FEATURES.md#capability-status).
Complete means the stated scope is available. Partially complete means a usable subset
is available with remaining work named. In progress means implementation has started
but is not available on the main branch. Planned means implementation has not started.
A written spec alone is planned. Completed scope belongs in the list below even when
an extension to the same capability remains in a tier.

Each row says what remains to be done and links to the spec that holds the design. Items
that extend an existing spec are designed in a "Roadmap follow-ups" section at the end of
that spec's Outcome, and the Outcome also records what has already landed. An item that
is partly finished stays in its tier, and its row describes only the remaining part.
Finished items are listed under [Completed](#completed).

The Size column estimates the remaining effort.

| Size | Meaning |
|---|---|
| S | Days |
| M | One to two weeks |
| L | Several weeks |
| XL | A quarter or more |

The Value column in Tiers 1 to 3 rates the impact of an item on the goal. Lower tiers are
ordered by their tier alone.

## Delivery priorities

The goal comes first. Sparkles should be the best graph database by objective measures,
which are correctness, conformance, performance, robustness and the standard features.
Embedded agent memory in C17 and C18 and the ontology platform of items 457 to 461, with
its editor, come second and run alongside each other. Shared entity representation in
A01 and C25 comes third. Applications built on top of Sparkles, such as the cyber and
public-health supply-chain pilot, come after these. The engine supplies generic
primitives, and domain adapters and matching logic stay application work rather than
engine infrastructure.

Complete named spec phases and their acceptance gates. A parent capability remains
partially complete while adopted requirements remain. Building an application on a
usable subset does not waive those requirements. Correctness, recovery, bounded
resources and source identity go ahead of unrelated feature expansion.

### Release

The first release fixes the storage formats that later versions must read and completes
backup. Item 343 settles the dataset-local codec settings, item 479 then sets the
first-release format cutoff, and item 61 completes backup. The feature waves below come
first, and these items take only capacity that the waves leave free. Published artifacts follow the first release: the server
binaries and container images of item 59 and the PyPI, Maven Central and npm packages of
item 58, both after the format cutoff. The later encryption phases of item 65, security and audit in item 466, the developer ecosystem of
items 468 and 47, notifications in item 46, the per-crate Nix builds of item 92 and the
replication refresh of item 280 follow the first release.

### Wave A: engine quality

Wave A holds the work that most improves the engine against objective measures.

* Competitive benchmark losses come first, as
  [BENCHMARKS.md](BENCHMARKS.md#where-sparkles-loses) records them.
* The benchmark gates of item 452 exist before any engine rewrite starts. Items 469 to
  473 add the eager-against-cursor forge matrix, the W3C suites under
  `execution=streaming`, `incr_bench` as a mise task, a demand and RDFS-on-read latency
  benchmark and an instruction-count screen. Each further loss that item 452's
  competitive coverage finds becomes its own Wave A item.
* Streaming execution follows through item 7.
* The first three stages of the unified executor, item 453, follow. The deletions of
  items 474 to 478 are complete, and items 480 to 483 have consolidated the execution
  policy, the reasoning mode, request building and rank fusion. The first-release format
  cutoff of item 479 and the commit publish tail of item 484 remain.
* Stage A of item 17 is complete with items 416 and 417, the reasoner witnesses and
  the fixed-point operator.
* Small items that finish a capability run in free capacity, such as item 77.

### Wave A2: engine rewrites

Wave A2 holds the rewrites that the Wave A gates protect. These are the accounting model,
shared kernels and executor merge of item 453, the join algorithms and estimation of item
454, the storage consolidation of item 455 and the reasoner core of item 456, which ends
with the incremental-maintenance core it shares with views. Each rewrite is measured on
forge before it lands. No query may be 5% or more slower on forge at 12 threads, and no
query under 0.3 ms may be slower on an Intel host.

### Wave B: memory and entities

Wave B starts with item 81 Phase 3, then items 341, 396 and 435 and the remaining C18
work. Item 12 can move its refresh onto an internal circuit now, and item 18 Phase 3
builds on the reasoner witnesses of item 416. The MCP tools of item 462 also belong to Wave B. They are the `ask` MCP tool in item 488, MCP tool
profiles in item 489 and a hybrid search tool that embeds query text in item 490.

### Wave C: ontology and data platform

Wave C builds the ontology and data platform of items 457 to 461 on item 71's axiom
model. The ontology syntax readers come first, followed by OWL classification and the
ontology workbench. The resource catalog of item 458 comes first on the data side,
followed by checks and protected merges, linked-data publishing and git export.
Fragment composition follows the storage consolidation of item 455. Wave C runs
alongside Wave A2 on the policy plumbing of items 480 to 483.

OWL classification continues in three streams once phase 4 of item 603 lands. Each
stream is held to the same speed target, which is three to five times as fast as the
fastest reference reasoner at the same reasoning level in every stratum, with a tie as
the floor.
1. Item 603's phases 5 to 8 run in order, as counting and data, then nominals, then the
   engine half of phase 7, then the final speed gate. The surfaces of phase 7, which
   expose `complete`, the incomplete classes and the consistency state, run beside them
   because they need only phase 4's API.
2. The cost of the Horn rules is worked as one piece. It covers the rest of item 693,
   the conclusion growth of item 710 that reproduces it on 13 axioms, and the
   individuals, functional data properties and top properties of item 692.
3. The cost of the EL engine is worked as one piece. It covers the cold runs on small
   files of item 709 and then the saturation memory of item 695.

The workbench UI runs as one stream of about two lanes beside the engine work. After the
DL Query tab, the SKOS editor and the web UI shell of item 632 come these, in order:
1. The ontology browser's rendering preferences (625), metrics (621) and the editor's
   trees on the hierarchy route (607), all on item 632's shell and item 631's command
   palette.
2. The design review of every page of item 633.
3. Inferred axioms in entity frames (622), with the inferred property and individual
   trees of item 609. Their explanation links wait for F24's justifications.
4. The visual SHACL shape editor of item 617.
5. Entity history (620), discussions (618) and watches (619), the last after the
   notifications of item 46.
7. Import resolution (624), bulk edits (626) and pattern-based axiom generation (623).
8. Vocabulary governance and change requests (627), after item 459.

Tagging documents with concepts (628) belongs to Wave B's ingest work, and real-time
co-editing (629) comes last.

### How the waves share capacity

The waves run in parallel, and each has its own capacity. Waves A2 and C take the
capacity first, and Wave B runs when a stream is free of them. When work competes for gate, review or benchmark time, the
dependency order and how ready the work is decide which goes first, not the wave it
belongs to. The goal at the start of this section states what Sparkles optimizes
for, and it does not order the waves.

The waves group the work by delivery, and the tiers below rate its value. A wave can
therefore hold items from several tiers. Within a wave, the order its section gives
applies, and across waves the dependency order and readiness decide.

### Production readiness

Production readiness runs alongside the waves. It covers items 60, 59 and 58 for the
API policy, server artifacts and packages, item 61 for backups and item 65 for
encryption, together with items 402 and 400. Item 64 and the adopted phases of 65 close
startup and key workflows. The format cutoff of item 479 lands before the release
artifacts of items 58 and 59, so the first release reads only the formats it supports.

### Deferred

Items 339 and 340 for durable jobs and maintained analyses, item 100 for report
configurations, the supply-chain application, item 20 for openCypher, item 72 for JSON
query languages and item 344 for ChatGPT-plan model access wait for the work above. A
prerequisite can bring one of them forward when a concrete use case needs it. Work
that depends on them waits with them. The data-change triggers of item 462 wait for item
339, the scheduled stored queries and updates of item 467 wait for item 339's durable
jobs, and the Bolt protocol of item 465 waits for item 20.

### Sequencing

Write-path competitive work goes before the commit-time maintenance part of item 17,
which is item 421, because both change the commit path. Item 421 then measures its cost
against the improved baseline.

Several workstreams have hard orderings.

* Item 7 lands before the executor merge of item 453.
* Items 446 and 447 land before the commit-path merge of item 455, which is the long-term
  half of its shared publish tail.
* Storage consolidation in X16 lands before fragment composition in X18.
* The format cutoff of item 479 lands before the release artifacts of items 58 and 59.
* The Horn-rule work of items 693, 710 and 692 lands before or between item 603's phases
  5 to 8, since both change the classifier's index in `classify/index.rs`.
* OWL classification in F24 stays separate from the reasoner core in F23. The two meet
  only through the F21 axiom model of item 71.

the competitive losses that Wave A lists. Preserve durability, cancellation and

not delay independent core phases, and retain their declared dependencies.

Virtual graphs in F19 and replication in F10 are substantial later phases of partial
specs. They remain visible completion work with explicit phase boundaries. They are not
prerequisites for the first memory workflow.

## Keeping this current

Update this document when an item ships, changes tier or gets a new spec. A new known gap
in a feature guide gets a roadmap item in the same commit. When an item ships, its spec's
Outcome records what landed, [FEATURES.md](FEATURES.md), the affected guide and the
relevant [benchmark report](benchmarks/README.md) change
in the same commit, and the Known gaps bullet drops the item's number. The item's row then
moves to a one-line entry under [Completed](#completed). When part of an item ships, its
row is cut down to the part that remains.
